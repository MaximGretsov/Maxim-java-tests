# Отчёт по настройке многопоточного запуска тестов

## Внесённые изменения

Для параллельного выполнения тестов была включена многопоточность JUnit 5:

```properties
junit.jupiter.execution.parallel.enabled=true

# Разные тестовые классы выполняются параллельно
junit.jupiter.execution.parallel.mode.classes.default=concurrent

# Используется фиксированный пул потоков
junit.jupiter.execution.parallel.config.strategy=fixed
junit.jupiter.execution.parallel.config.fixed.parallelism=N
junit.jupiter.execution.parallel.config.fixed.max-pool-size=N
```

В ходе эксперимента значение `N` последовательно изменялось от 3 до 9. Параллельное выполнение происходило на уровне тестовых классов, а методы внутри одного класса выполнялись последовательно.

Для корректной работы в нескольких потоках использовались независимые тестовые пользователи и аккаунты. После завершения тестов созданные пользователи удалялись. UI-тесты запускались в отдельных браузерных сессиях.

В процессе работы также был изменён `UserSessionExtension`. Создание и подготовка тестового пользователя были вынесены на уровень тестового класса, благодаря чему один пользователь мог использоваться всеми тестовыми методами этого класса вместо создания нового пользователя перед каждым тестом. После завершения класса пользователь удалялся.

Изменение `UserSessionExtension` не дало заметного улучшения общего времени прогона, однако сделало тесты корректнее с точки зрения работы с тестовыми данными и уменьшило количество операций создания, авторизации и удаления пользователей, снизив нагрузку на базу данных.

Для контрольного последовательного запуска многопоточность была отключена:

```properties
junit.jupiter.execution.parallel.enabled=false
```

Во всех запусках выполнялся одинаковый набор из **64 тестов** командой:

```powershell
mvn clean test
```

Все рассматриваемые прогоны завершились успешно, без ошибок и падений.

## Результаты замеров

Под **чистым временем тестов** указана сумма длительностей тестов наиболее загруженного потока. Для последовательного запуска это сумма длительностей всех тестов в потоке `main`.

**Запуск и служебные операции** рассчитаны как разница между общим временем Maven и чистым временем тестов. Это расчётное значение, включающее компиляцию, подготовку окружения, создание браузерных сессий, хуки и другие накладные расходы, а не отдельно измеренное время запуска приложения.

| Конфигурация | Потоков | Запуск и служебные операции | Чистое время тестов | Общее время Maven | Результат |
|---|---:|---:|---:|---:|---|
| Без параллелизации | 1 | 34.500 с | 61.500 с | 96.000 с | Успешно |
| Параллельный запуск | 3 | 16.746 с | 28.781 с | 45.527 с | Успешно |
| Параллельный запуск | 4 | 23.648 с | 22.300 с | 45.948 с | Успешно |
| Параллельный запуск | 5 | 21.310 с | 26.437 с | 47.747 с | Успешно |
| Параллельный запуск | **6** | 21.835 с | 22.724 с | **44.559 с** | Успешно |
| Параллельный запуск | 7 | 22.604 с | 22.964 с | 45.568 с | Успешно |
| Параллельный запуск | 8 | 22.976 с | 22.823 с | 45.799 с | Успешно |
| Параллельный запуск | 9 | 23.023 с | 23.010 с | 46.033 с | Успешно |

## Выводы

Лучший результат получен при использовании **6 потоков**: полный прогон занял **44.559 секунды**.

По сравнению с последовательным запуском:

- время выполнения сократилось на **51.441 секунды**;
- общее время уменьшилось на **53.6%**;
- тесты стали выполняться примерно в **2.15 раза быстрее**.

Увеличение количества потоков свыше шести не дало дополнительного ускорения:

| Сравнение с 6 потоками | Увеличение времени |
|---|---:|
| 7 потоков | +1.009 с |
| 8 потоков | +1.240 с |
| 9 потоков | +1.474 с |

После шести потоков дальнейшее увеличение параллелизма не привело к ускорению. Наиболее вероятное ограничение связано с одновременным запуском нескольких браузерных сессий и параллельными обращениями тестов к одному backend-сервису.

При 7–9 потоках дополнительная конкуренция за процессорное время, память, браузерные ресурсы, сеть и серверные операции стала компенсировать выгоду от увеличения количества потоков. Поэтому общее время прогона перестало уменьшаться и начало незначительно расти.

Точно разделить влияние браузеров, процессора и backend-сервиса по представленным логам нельзя, поскольку показатели CPU, RAM и нагрузки на сервер отдельно не измерялись.

Изменение `UserSessionExtension` не повлияло заметно на скорость выполнения тестов. Его основной результат — уменьшение количества создаваемых тестовых пользователей и связанных обращений к backend и базе данных. Поэтому изменение рассматривается не как оптимизация времени прогона, а как улучшение организации тестов и снижение лишней нагрузки на тестовое окружение.

**Оптимальной конфигурацией для текущего набора тестов является фиксированный пул из 6 потоков.**
